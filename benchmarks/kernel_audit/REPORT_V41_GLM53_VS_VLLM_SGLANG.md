# Kernel quality: DeepSeek-V4.1-Flash and GLM-5.3-Flash vs vLLM and SGLang

Date: 2026-11-09. This is a source comparison, not a new timing run.

MoE-Infinity numbers below are the 2026-11-01 measurements on one RTX PRO 6000 Blackwell Max-Q (sm_120, 188 SMs, 300 W) in [REPORT.md](REPORT.md). Nothing here was re-timed. vLLM and SGLang are upstream `main` as fetched the same day:

- vLLM `e19e540a9e5f`
- SGLang `e60f7e909bfb`

Local checkouts under `/mnt/raid0nvme0/leyang/vllm` (v0.20.2rc0, May 2026) and `sglang` (v0.5.14, June 2026) do not contain these models and were not used.

The comparison is module by module, on six axes from the existing audit: native low-precision MMA versus a dequant-to-BF16 round trip, one grouped launch versus one launch per expert, fusion, host syncs, CUDA graph, and what actually runs on **sm_120**. This GPU has no `tcgen05` / TMEM, and the opt-in dynamic shared-memory cap is about 99 KB. Datacenter Blackwell (sm_100 / sm_103) is named only where the source takes a different kernel there.

---

## Verdict

On both models the gap is the same shape. MoE-Infinity still dequantises the checkpoint into BF16 and then runs a per-expert GEMM. vLLM and SGLang keep the checkpoint precision inside a grouped MoE kernel, and they have real sparse-attention, indexer, compressor, mHC, and speculative-decoding kernels. On sm_120 those stacks do **not** get the sm_100 mega-kernels (`tcgen05`, FlashMLA mega-attention, TRT-LLM MoE). They fall through to the next grouped kernel that the device gate allows. That fallback is still a different class of implementation from a per-expert dequant.

Measured on this GPU, the MoE-Infinity production expert layer sits at **6–7 % of DRAM** for DeepSeek-V4.1-Flash (`v4_fp4_prod`) and **12–13 %** for GLM-5.3-Flash (`fp8_prod`) at decode batch 1 through 256 ([REPORT.md](REPORT.md) §3.1). The same shapes on a BF16 grouped GEMM are memory-saturated. No vLLM or SGLang timing is claimed here.

## What sm_120 specifically does not get

Both upstream trees treat sm_120 as Blackwell for capability checks and then exclude it from the `tcgen05` kernels. `is_sm100_supported` in SGLang is capability major 10 only. The comment next to it says datacenter Blackwell plus sm_110, and that consumer Blackwell is sm_120.

| Kernel | sm_100 / sm_103 | sm_120 |
|---|---|---|
| V4.1 MoE, vLLM | `TrtLlmMxfp4ExpertsMonolithic` (MXFP4 × MXFP8, fused SwiGLU) | `DeepGemmFP4Experts` if DeepGEMM loads; else Marlin |
| V4.1 MoE, SGLang | `Mxfp4FlashinferTrtllmMoEMethod` | `Mxfp4FlashinferCutlassMoEMethod` (MXFP8 activations × MXFP4) |
| GLM-5.3 MoE, vLLM | TRT-LLM grouped block-128 FP8 | `TritonOrDeepGemmExperts` when DeepGEMM loads. Decode batch 1 is below the M alignment, so that step is the Triton leg. If DeepGEMM does not load, grouped `TritonExperts` |
| GLM-5.3 MoE, SGLang | TRT-LLM grouped block-128 FP8 | Grouped Triton for both phases, unless an expert-parallel A2A backend turns DeepGEMM on |
| V4.1 attention | FlashMLA mega-attention, one fused launch | vLLM: FlashInfer DSV4 sparse, if that specialization is installed. SGLang: Triton FlashMLA, or PyTorch if the flag is off. Tilelang's 141 KB smem request does not launch |
| V4.1 `wo_a` fuse, mega-mHC, CuTe all-reduce, MXFP4 indexer cache, fused MQA top-k | Present, behind family-100 gates | Absent. SGLang `wo_a` fuse is major == 10 |
| GLM DSA on SM120 | TRT-LLM sparse MLA | vLLM can take `FLASHINFER_MLA_SPARSE_SM120` at top-k 2048. SGLang's `flashinfer_sparse_mla` implementation refuses this architecture and leaves the model on `trtllm` |
| GLM KDA decode | FlashInfer `recurrent_kda` (SGLang) or Triton recurrent (vLLM) | SGLang: Triton. vLLM: Triton recurrent. FlashKDA prefill is allowed on SM12x in vLLM |

The 99 KB shared-memory cap shows up in three places that are already in the source: MoE-Infinity's tilelang `sparse_attn` (141 KB), SGLang's Triton sparse-MLA head cap (`BLOCK_H` 64/128 spills on sm_120 above 32 heads), and the vLLM GPT-OSS MXFP4 comment that the OAI Triton kernels are tile-capped at 99 KB. The DeepSeek V4.1 selector does not use that Marlin preference; the GPT-OSS function is a different priority list (`_get_priority_backends_for_gpt_oss`).

## Measured layer time, 2026-11-11

One expert layer. MoE-Infinity and the GLM columns ran on GPU 5, the same Max-Q part as [REPORT.md](REPORT.md). Synthetic weights, cold experts, 10 CUDA-event iterations. MoE-Infinity is the production dequant path (`fp8_prod`, `v4_fp4_prod`). The GLM vLLM 0.30.0 and SGLang 0.5.23 cells are their grouped FP8-block-128 Triton kernels (E=288, H=4096, I=2048, top-8). Neither had a tuned config for this GPU name, so those cells are the default tile. Script: `benchmarks/kernel_audit/bench_external_grouped_moe.py`. The V4.1 vLLM and SGLang cells are the MXFP4 kernels described under the table.

| Model | Point | Experts launched | MoE-Infinity | vLLM | SGLang |
|---|---|---:|---:|---:|---:|
| GLM-5.3-Flash | b1 | 8 | 0.89 ms | 0.22 ms | 0.23 ms |
| GLM-5.3-Flash | b64 | 241 | 26.2 ms | 4.54 ms | 4.57 ms |
| GLM-5.3-Flash | 1K | 288 | 32.3 ms | 4.77 ms | 4.72 ms |
| GLM-5.3-Flash | 12K | 288 | 52.6 ms | 19.2 ms | 17.6 ms |
| DeepSeek-V4.1-Flash | b1 | 6 | 1.06 ms | 1.39 ms | 0.25 ms |
| DeepSeek-V4.1-Flash | b64 | 244 | 43.4 ms | 1.43 ms | 6.92 ms |
| DeepSeek-V4.1-Flash | 1K | 384 | 68.3 ms | 2.19 ms | 8.05 ms |
| DeepSeek-V4.1-Flash | 12K | 384 | 82.6 ms | 11.2 ms | 19.0 ms |

Dividing MoE-Infinity wall time by the experts launched (and by 4 streams for GLM) gives about 440 µs per GLM expert and 178 µs per V4.1 expert, flat from batch 1 through 1K. The layer is a loop of dequant-to-BF16 plus a tiny GEMM. The grouped FP8 kernels are one launch.

`v4_moe_forward_sm120_pro6000` with `act_block=32`, the same shapes and expert counts, measured on this GPU the same day: **0.053 ms, 2.81 ms, 6.68 ms, 15.9 ms**. That is the existing grouped kernel, not the Path B loop. The moe-store V4.1 forward calls it when the extension exports the symbol and the RTX PRO 6000 gate passes; a build that only has `v4_expert_forward` stays on the loop. The implementation plan is `docs/superpowers/plans/2026-11-11-grouped-moe-v41-glm53.md`.

The V4.1 vLLM and SGLang cells were measured on GPU 4, the other Max-Q part, the same day. SGLang is FlashInfer CUTLASS `cutlass_fused_moe` with MXFP8 activations and MXFP4 weights, SwiGLU inside the kernel, checkpoint scales already interleaved, and the activation quant call outside the timer (`results/framework_bench/mxfp4_grouped.json`). vLLM is two calls to vendored DeepGEMM `m_grouped_fp8_fp4_gemm_nt_contiguous` (gate+up, then down). SwiGLU, the FP8 requant between them, and the token permute are outside that timer, so those cells are a lower bound on `DeepGemmFP4Experts.apply` (`results/framework_bench/vllm_mxfp4_grouped.json`). Batch 1 uses 6 rows; the other three points give every one of the 384 experts an equal share of `tokens × 6` rows. Round-robin at batch 64 therefore touches 384 experts, while the MoE-Infinity row uses the audit's expected 244.

## What is not claimed

- The 2026-11-09 source comparison did not time vLLM or SGLang. The GLM rows are the 2026-11-11 grouped FP8 Triton timing on untuned default tiles. The V4.1 vLLM column is two DeepGEMM GEMMs and the SGLang column is the fused CUTLASS MoE. A tuned tile or a full expert-module wrapper can move those cells.
- MoE-Infinity expert-layer percentages assume resident weights and uniform routing. Offload makes PCIe the roof, and the kernel gap matters on hits ([REPORT.md](REPORT.md) §8).
- "Auto" means the backend each tree selects when the user does not pass a MoE or attention backend. An explicit flag can pick Marlin, TileLang, or DeepGEMM on either stack.
- Correctness of the sm_120 attention fallbacks (SGLang `trtllm` DSA for GLM-5.3-Flash, FlashInfer specialization presence) was not executed here. The source section is the gate each tree applies. The timing section is the kernel measurement.
